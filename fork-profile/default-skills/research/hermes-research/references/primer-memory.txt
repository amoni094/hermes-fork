PRIMER: Memory Architecture in LLM Agents


CORE CONCEPTS

Memory in LLM agents divides into three cognitive classes. Episodic memory stores bounded, time-stamped events from prior interaction runs — "what happened in session X." Semantic memory stores context-free facts and relationships — "what is true about the world." Procedural memory stores executable knowledge — "how to accomplish task class Y." The distinction matters because each class has different write frequency, decay rates, and retrieval access patterns.

Retrieval-Augmented Generation (RAG) is the baseline: embed queries and stored items in the same vector space, retrieve by cosine similarity at inference time. Condition: RAG assumes query and memory live in a common semantic neighbourhood and that the most similar item is the most useful one. Both assumptions fail for sequential tasks (where the relevant memory is the prior step's outcome, not the semantically-nearest fact) and for procedural lookup (where trigger-match outperforms embedding similarity).

Memory consolidation is the post-hoc compression of episodic traces into semantic summaries, reducing retrieval noise by converting high-dimensional event logs into low-dimensional abstract representations. The critical theorem: consolidation only helps if the summary preserves the retrievable distinction between items that the raw episodes encoded. Lossy summarisation that collapses behaviorally distinct situations degrades performance.

Write-then-read consistency is the constraint that a memory written at time T must be queryable with correct results at T+1. LLM pipelines frequently violate this: facts written to staging during a session are not yet indexed for retrieval, causing agents to re-derive facts they nominally stored.

Temporal decay: item utility U(t) decays as U(t) = confidence * exp(-lambda * age) * log(1 + access_count), where lambda varies by memory class (episodic: ~0.05/day, semantic facts: ~0.01/day, procedural: ~0.002/day). This is the Ebbinghaus retention model applied to AI memory stores; lower lambda means slower decay. Items below a utility threshold should be archived, not deleted, since reactivation (reconsolidation) is cheaper than re-extraction.

Working memory is the agent's active context window. Its hard limit creates a bottleneck: the empirical token cost of conversation history grows multiplicatively with turns (5 tools = 2.1x tokens; 2 additional turns = 12.1x tokens), not additively. This means history compression has higher ROI than tool pruning.

Key empirical result: EKV (external key-value dense retrieval) is the dominant strategy at long horizons. On LoCoMo, EKV achieves Recall@5 = 0.573 where all other strategies (graph memory, summarisation, in-context windowing) collapse to Recall@5 < 0.005. Retriever quality dominates memory construction complexity: upgrading the retriever alone shifts accuracy 58% to 76% on a fixed memory store.


COMPONENT ANALYSIS


l1-extract

(a) Mathematical structure. l1-extract is an extraction function f: session_transcript -> {(fact_i, entity_i, type_i, confidence_i, timestamp_i)}. Formally this is an information extraction problem: identify spans in text, classify them into memory_type (fact / correction / outcome / preference / reasoning), and assign a confidence score. The ideal extractor maximises precision (no hallucinated facts) and recall (no dropped facts) simultaneously — a standard precision-recall tradeoff with an F1 optimum.

(b) What Hermes does. l1-extract runs a prompted LLM over the session transcript to emit structured YAML with memory_type tags, entity annotations using POLE+O schema, and a confidence score it assigns itself. The problem: the extractor and the confidence scorer are the same model — this is an EIA violation (Echo-Indexed Assessment). The confidence scores are correlated with the extractor's errors, so incorrect facts get inflated confidence and get over-retrieved.

(c) Principled approach. Route confidence assessment through an independent signal. Use the contradiction_check NLI score from l1-promote as the authoritative confidence gate, not the extractor's self-reported score. Gate promotion: if NLI finds a stored fact that CONTRADICTS the extracted fact with confidence >= 0.75, invalidate the old fact and assign the new one confidence = NLI_confidence, not extractor_confidence. For new facts with no contradiction signal, use extraction_confidence only as a prior, not a final score.

(d) Value assessment. High value, low cost. The EIA fix requires a single code change in l1-promote.py: read the NLI score and override the raw extraction_confidence for promoted facts. Risk: NLI models can be miscalibrated on domain-specific assertions. Validate by sampling 50 extracted facts, manually scoring their accuracy, and correlating manual score against NLI-corrected confidence vs raw extractor confidence. Expect NLI-corrected confidence to track manual accuracy better.


l1-promote

(a) Mathematical structure. l1-promote is a boundary controller: it implements a retention policy over the staging buffer. The decision function is a binary classifier: promote(fact) = 1 if retention_score(fact) > threshold AND not_duplicate AND not_retracted. retention_score = confidence * exp(-lambda * days_in_staging) * log(1 + access_count). Deduplication is a nearest-neighbour lookup: if cosine(embed(fact), embed(stored_memory)) >= 0.92, skip promotion and increment access_count on the existing memory.

(b) What Hermes does. The dedup gate, NLI contradiction check, Ebbinghaus retention score, and lifecycle status (Active/Archived/Deleted) are implemented. The engram maturation gate (require access_count >= 2 before promoting to Hindsight) is documented but not enforced in the current pipeline. Write-then-read consistency is partially satisfied: facts in staging.md are not retrievable via hindsight_recall until the promote job completes.

(c) Principled approach. Add the engram maturation gate as a hard gate in l1-promote, not a soft heuristic. Concretely: if a fact appears in only one session's staging.md and has no access_count > 0 from prior dedup hits, hold it in staging for one additional session cycle before promoting. This matches the neuroscience result that consolidation into long-term memory requires at least two encoding events. Also enforce the non-revival rule: before promoting any fact, check the retraction ledger at ~/.hermes/memory-facts/retractions.log. A previously retracted fact that re-appears in a new session must go to a review queue, not to Hindsight.

(d) Value assessment. Medium value, low cost. The engram gate will reduce Hindsight growth rate and improve precision of long-term memory at the cost of delayed availability for one-shot facts. Validate by measuring false-positive rate in Hindsight before and after gate activation (sample 100 stored facts, manually classify as accurate/inaccurate). Risk: single-occurrence facts that are genuinely important get delayed by one session. Mitigation: add a high_confidence bypass (if extractor_confidence >= 0.9 AND NLI finds no contradiction, promote immediately).


Hindsight bank

(a) Mathematical structure. Hindsight is an EKV (external key-value) store: keys are embeddings, values are (text, metadata, lifecycle_status). Retrieval is approximate nearest-neighbour search with optional metadata filters. Relevance rank: score = 0.6 * cosine_similarity + 0.25 * recency + 0.15 * access_frequency. AgentMemBench (arXiv:2608.00009) establishes EKV as dominant at long horizons (Recall@5 = 0.792); Hindsight's design is architecturally correct.

(b) What Hermes does. hindsight_recall uses semantic similarity. The temporal reranking coefficients (0.6 / 0.25 / 0.15) are written as metadata stubs but the Hindsight query hook that applies them is not yet wired in. The retrieval strategy is static: the same dense-search-first path fires for all query types regardless of whether the query is temporal, relational, or procedural.

(c) Principled approach. Wire the query-type router (memory-query-router.py, already implemented) as a preprocessing step before every hindsight_recall call. Temporal queries go to hindsight_temporal sort first; relational queries go to Graphiti first; procedural queries go to session_search first. This is the ERSkill insight: retrieval strategy should be a function of query type, not a fixed pipeline. After anchors are retrieved, do one ripple expansion: issue a follow-up mcp__graphiti__search_memory_facts call with the entity names from anchor results. This approximates RippleMem's one-hop expansion at zero infrastructure cost and is expected to add +3 to +12% recall on relational queries.

(d) Value assessment. High value, medium cost. Query routing is already implemented; wiring it requires intercepting hindsight_recall calls at the agent turn boundary and dispatching through the router. Risk: the router heuristics are keyword-based and will misclassify ambiguous queries. Track misclassification rate by logging (query_type, strategy_used, recall_success) to the l1-extract pipeline for 20+ sessions, then promote the top-2 strategies per type.


Memory TTL purge

(a) Mathematical structure. TTL purge is a threshold function on the utility score: if U(fact, t) < archive_threshold, move to archived; if U(fact, t) < delete_threshold, remove. With type-conditioned decay (ScrubJay-MEM, arXiv:2608.04746), lambda and the decay timescale tau vary by memory_type: ephemeral (pi=0.9, tau=2h), task_specific (pi=0.6, tau=24h), procedural (pi=0.3, tau=10d), factual (pi=0.1, tau=45d).

(b) What Hermes does. TTL is a global duration config in config.yaml, applied uniformly across memory_types. This treats a one-off ephemeral fact (today's search result) with the same decay rate as a stable procedural fact (how to configure ProtonVPN).

(c) Principled approach. Implement type-conditioned perishability from ScrubJay-MEM. The retrieval score becomes: score = semantic_score * exp(-pi * age / tau) where pi and tau are looked up from the memory_type tag already written by l1-extract. This requires adding three columns to the Hindsight SQLite schema: perishability (pi), tau_sec, inserted_at. The purge cron reads these and computes per-fact decay scores rather than applying a global TTL. ScrubJay-MEM is the only evaluated retrieval system with positive GenGap (+0.108); ablating type-conditioned decay collapses GenGap 5.7x.

(d) Value assessment. High value, medium cost. The schema migration is the main risk: existing Hindsight entries lack pi/tau fields and will need a default assignment at migration time (use factual defaults: pi=0.1, tau=45d). Validate by comparing retrieval precision before and after on a manually-curated test set of 50 queries with known correct answers drawn from sessions at varying ages.


working-memory.py

(a) Mathematical structure. Working memory management is a knapsack problem: maximise information value packed into a fixed token budget C. Value is a function of item relevance to current task, recency, and utility. The per-turn tool schema width is the dominant cost term; conversation history depth is the dominant multiplier. Optimal working memory policy: fill tool schemas last (lowest value-per-token at the margin), fill history summaries first.

(b) What Hermes does. Context compression fires when context length hits a configured ratio threshold. Compression is LLM summarisation — the last resort, not the first. The 3-tier cascade (offload large tool results to filesystem pointer, evict stale write args, summarise as last resort) is documented as a pattern but not all tiers are implemented.

(c) Principled approach. Enforce the 3-tier cascade strictly: any tool result exceeding 4K tokens is offloaded to ~/.hermes/offload/SESSION_ID/ with a pointer injected into context instead of the full content. At 85% context capacity, evict the oldest write/edit argument blocks (low future-retrieval value). LLM summarisation fires only at 95%+ capacity. Additionally, inject the top-5 Hindsight facts relevant to the current task into the context preamble at session start (Agent Lifespan Engineering, arXiv:2605.26302), so the agent begins with preloaded relevant memory rather than re-retrieving mid-task.

(d) Value assessment. High value for long sessions, low cost for the filesystem offload tier (straightforward tool-result interception), medium cost for the preamble injection (requires a session-start hook). Risk: preamble injection can inject stale or irrelevant facts if the session-start query is too broad. Validate by tracking re-buy rate (fraction of hindsight_recall calls that retrieve a fact already present in context) — target below 10%.


Graphiti (knowledge graph)

(a) Mathematical structure. Graphiti is a bi-temporal property graph: nodes are entities, edges are typed relations with (valid_from, valid_to, superseded_by) fields. Fact update is a logical operation, not a physical delete: asserting a contradiction sets valid_to = now on the old edge and creates a new edge. Multi-hop retrieval is graph traversal: answer relational queries by path traversal rather than by vector lookup alone.

(b) What Hermes does. Graphiti ingests POLE+O-typed entities from l1-graphiti-write.py. The bi-temporal schema is wired. Multi-hop traversal is available via mcp__graphiti__search_memory_facts but is not used as a systematic fallback after flat hindsight_recall. AgentMemBench shows graph memory (GEM class) underperforms dense retrieval at long horizons; Graphiti alone should not be the primary retrieval path.

(c) Principled approach. Position Graphiti as the relational query specialist, not the default retrieval path. Route queries with "who / which / relationship / connected" semantics to Graphiti first, then fall back to Hindsight for any entity not found in the graph. Implement one-hop ripple expansion after every hindsight_recall anchor retrieval: for each entity name in the returned facts, call search_memory_facts with that entity as the seed. This surfaces supporting evidence the anchor retrieval misses and is the zero-infrastructure approximation of RippleMem (+3 to +12% recall). Dedup relations at ingest: label count should be collapsed from 360+ to ~80 canonical labels before multi-hop traversal produces reliable results.

(d) Value assessment. Medium value, medium cost. The ripple expansion wrapper is a 20-line function. The relation-label collapse is higher effort and requires a schema migration on the existing graph. Validate ripple expansion by running 20 relational queries (queries about entity relationships) against Hindsight-only vs Hindsight+one-hop Graphiti, scoring recall manually.


RANKED IMPLEMENTATION CANDIDATES


1. Type-conditioned perishability decay in TTL purge
What: Replace the global TTL in config.yaml with per-fact pi and tau fields derived from the memory_type tag, using the ScrubJay-MEM decay formula for retrieval scoring and pruning.
Expected benefit: Ephemeral facts expire within hours while procedural facts persist for weeks, reducing retrieval noise and improving relevance scores — the only evaluated retrieval modification with documented positive GenGap.
Implementation cost: SQLite schema migration to add three columns, update l1-promote.py to write pi/tau at ingest, update purge cron to use the formula — estimated two to four hours of code changes.


2. Query-type router wired to hindsight_recall
What: Intercept every hindsight_recall call through the already-implemented memory-query-router.py, dispatching temporal queries to time-sorted retrieval, relational queries to Graphiti first, procedural queries to session_search first.
Expected benefit: 10 to 30% reduction in irrelevant retrieved facts for non-semantic queries, with no increase in infrastructure cost since the router script already exists.
Implementation cost: One session-boundary hook that wraps hindsight_recall calls — estimated two to three hours; risk is keyword misclassification on short queries.


3. Working memory preamble injection at session start
What: At the beginning of each session, query hindsight_recall with the session's initial task description and inject the top-5 returned facts into the context preamble before the first turn executes.
Expected benefit: Reduces mid-session re-buy rate (agent retrieving facts it should have had from session start) and eliminates redundant hindsight_recall calls for stable facts, cutting both token cost and retrieval latency.
Implementation cost: A session-start hook in the harness that runs one hindsight_recall call and prepends results to the system prompt — estimated one to two hours; risk is injecting irrelevant facts for sessions whose task differs from prior sessions, mitigated by keeping the preamble to five facts maximum.
