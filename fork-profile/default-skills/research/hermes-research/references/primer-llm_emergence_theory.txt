PRIMER: Emergence and Scaling in LLMs

---

FIELD OVERVIEW

Emergence and scaling in LLMs studies how and why model capabilities appear discontinuously as model size, data volume, and compute increase. The field combines empirical scaling law measurement (Chinchilla, Kaplan et al.), phase transition theory from statistical physics, and mechanistic interpretability to predict and explain capability jumps. Core objects: loss curves as functions of model size N and data D, emergence thresholds where qualitative new abilities (arithmetic, reasoning, in-context learning) suddenly activate, and grokking phenomena where generalization lags memorization by orders of magnitude. Why it matters mathematically: scaling laws determine resource budgets for production systems; emergence thresholds tell you which problems need which model sizes; understanding in-context learning (ICL) as implicit Bayesian inference lets you predict when few-shot prompting will fail. This directly impacts agent system design because agents face a continuous choice: route to a smaller, cheaper model or escalate to one that may have crossed an emergence threshold for the subtask.

---

KEY RESULTS

Chinchilla Optimality (Hoffmann et al., 2022): Optimal compute allocation balances model size N and training tokens D such that N ≈ D / 20 (roughly equal flops spent on model scale vs. data scale). For a fixed compute budget C, optimal N ≈ sqrt(C / (6 * D_per_param)), meaning do not scale model size alone. Practical formula: if you have 1e24 flops, use ~70B params with ~1.4T tokens, not 175B with 500B tokens.

Emergent Abilities (Wei et al., 2022): Certain tasks (few-shot arithmetic, multilingual translation, logical reasoning) show smooth loss curves but sharp accuracy jumps at specific model scale thresholds. These are not guaranteed phase transitions—some emerge smoothly—but empirically many do at scales around 1B-70B params for reasoning. Threshold is task-dependent and often unpredictable a priori.

In-Context Learning as Implicit Inference (Akyürek et al., 2022; Xie et al., 2023): ICL operates as Bayesian inference over task-specific parameters. When a model reads a prompt with examples, it approximates computing a posterior over hypotheses. ICL success probability increases with: (1) example quality, (2) task structure simplicity, (3) model scale. Failure modes: tasks with high hypothesis space (reasoning over complex multi-hop logic), irreducible noise, or distribution mismatch.

Grokking and Delayed Generalization (Power et al., 2022): Training loss drops immediately, but test accuracy lags by orders of magnitude of training steps. Grokking occurs in algorithmic tasks. Practical implication: models can memorize tool signatures and basic patterns long before generalizing to novel tool combinations, affecting when to trust a model on unseen tasks.

Token Scaling vs. Model Scaling: Doubling tokens typically improves loss more efficiently than doubling model size at large scales (Hoffman et al.). This favors longer context, better data, and iterative refinement over raw parameter count for fixed budget.

---

STANDARD PRACTITIONER TOOLS

Scaling law calculators: Use Chinchilla loss formula L(N,D) ≈ A + B/N^α + C/D^β (α≈0.07, β≈0.8) to predict loss at new scales. Libraries: chinchilla (DeepMind), palimpsest (scaling simulators). Implementations: log-linear regression on empirical runs to fit your own coefficients.

Capability probes: Benchmark suites (MMLU, GSM8K, ARC) track emergence. Run these at model checkpoints to identify thresholds. Automated threshold detection: fit sigmoid curves to accuracy vs. log(N), solve for inflection point.

ICL diagnostics: (1) Vary example count and measure accuracy plateau. (2) Swap example order; if performance drops sharply, model is doing pattern matching, not inference. (3) Measure in-context adaptation speed: present task, measure loss decay per new example.

Grokking detection: Train small models to completion on held-out tasks. Plot train/test divergence over time. If divergence narrows sharply after N steps, suspect grokking; set validation window to 3-5x observed grokking lag.

HERMES APPLICATIONS

APPLICATION 1: Model Routing (Subtask → Model Selection)

Mathematical structure: Routing is a decision problem under uncertainty. Each subtask t has a true difficulty d_t (unknown). Each model m has a capability frontier C_m(scale, training_data). Route to m if E[cost(m,t)] < threshold AND E[success(m,t)|history] > min_success. Emergence theory tells us: (1) capability is not smooth—small scale jumps in hard reasoning cause sudden success shifts; (2) ICL quality depends on prompt structure, so identical subtasks may have different effective difficulties depending on few-shot context.

Current Hermes: Heuristic routing based on task type keyword matching ("summarize" → Mistral-Small, "reasoning" → Claude). Fixed per-task-type. No measurement of actual model success on held-out subtasks.

Principled approach: Maintain a per-model, per-task-class success rate matrix S[model][task_class] updated online. Fit logistic regression: success_prob = sigmoid(w0 + w_model + w_task + w_tokens_remaining). Before routing, query the model's emergence threshold for the task class (via micro-benchmarks run offline). If your token budget is below the threshold, route to largest available model or reject task. Use Thompson sampling to balance exploration (try cheaper models) vs. exploitation (route to known winners). Concretely: every 10th occurrence of task class "multi-step reasoning," route to Mistral-Small even if history says Claude; measure success; update posterior.

Value assessment: High value, medium lift. You already have task history; adding offline emergence benchmarks (MMLU subset, GSM8K for reasoning, etc. per task class) is 1-2 weekend. Risk: emergence thresholds measured offline may not transfer to your specific task distribution or prompting style (cold-start problem). Mitigation: run emergence probes on your actual task distribution, not generic benchmarks. Expected ROI: 10-15% cost reduction if you avoid unnecessary Claude escalations, plus faster latency (Mistral-Small is 2-3x faster).

APPLICATION 2: Token Budget Allocation Across Multi-Step Tasks

Mathematical structure: Chinchilla and token-scaling results say that for fixed compute, allocating more tokens to better data (longer reasoning chains, more examples) beats allocating to bigger models. For Hermes: you have a global token budget per day. Each delegate_task spawns subagents; each uses context_compression to prune history. The question is: how much context should each subagent retain, and should you allocate tokens to running a second pass (re-reasoning with more examples) or calling a bigger model once?

Current Hermes: Context compression is trigger-based (history > 50K tokens). No principled budget allocation; each subagent gets equal tokens. No re-ranking or multi-pass.

Principled approach: Model the task as a computation tree. Each node is a subtask; each edge is a token cost. Use a variant of optimal substructure: for a subtask sequence [t1, t2, ..., tn] with budget B, allocate tokens to minimize E[error]. From scaling law theory: error ∝ 1/sqrt(D) (data scaling). If you have budget to do one pass with D tokens vs. two passes with D/2 each, two passes win if the second pass has different task structure (e.g., verification). Concretely: before starting a multi-step task, run a planning phase (cheap, small model): decompose the task, estimate tokens per subtask using a learned predictor (train offline on your task logs). Use dynamic programming: memo[i][b] = min error over first i subtasks with b tokens. Allocate tokens accordingly. Route each subtask using the routing matrix from APPLICATION 1, but gate by allocated tokens.

Value assessment: Very high value, high lift. Requires offline training of a token-predictor model (feed it task description, outputs estimated tokens). Also requires instrumenting all subtasks to record actual tokens spent (mostly done). Risk: token predictor may not generalize to new task types; over-optimizing for budget may sacrifice quality. Mitigation: use a Bayesian predictor with uncertainty; allocate +20% buffer. Expected ROI: 20-30% token savings on multi-step tasks; better completion rates under budget pressure.
