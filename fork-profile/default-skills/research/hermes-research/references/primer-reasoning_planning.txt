PRIMER: Reasoning and Planning in LLM Agents


CORE CONCEPTS

Chain-of-thought (CoT) reasoning prompts a language model to emit intermediate steps before a final answer. The key empirical result (Wei et al. 2022): on multi-step arithmetic and commonsense tasks, CoT elicits significantly higher accuracy than direct prompting, but only for models above roughly 100B parameters — smaller models show flat or negative transfer. The mechanism is not fully understood but is best modeled as approximate program execution over a latent reasoning graph.

Self-consistency (Wang et al. 2023) samples k independent reasoning chains and takes a majority vote over final answers. This reduces variance proportional to 1/sqrt(k) under the assumption that correct chains share final answers and errors are uncorrelated — an assumption that breaks when systematic model biases are present.

Tree-of-thought (ToT, Yao et al. 2023) frames reasoning as a search problem over a tree where nodes are partial reasoning states and edges are generation steps. A value function V(s) scores each node; the algorithm applies BFS or DFS with pruning. MCTS extends this: nodes store visit count N(s) and accumulated value Q(s), with selection via UCT = Q(s)/N(s) + c * sqrt(ln N(parent)/N(s)). This enables principled lookahead at the cost of O(k*d) model calls for branching factor k and depth d.

Process Reward Models (PRMs, Lightman et al. 2023) assign per-step scores rather than only scoring final outcomes. The key theorem: under sparse-reward credit assignment, PRMs converge faster and more stably than Outcome Reward Models (ORMs) because they reduce the effective horizon. Empirically on MATH benchmarks, PRMs trained on process annotations outperform ORMs with equivalent compute.

Verifier-guided search combines a generator model P(step|state) with a learned verifier V(state) to implement beam search: retain top-b states by V at each step. Symbolic-neural hybrids add a deterministic planner (PDDL-style or graph traversal) as a subroutine callable by the neural agent, which handles domains with hard constraints better than pure neural generation.


COMPONENT ANALYSIS


Agent Loop Reasoning Quality

(a) The per-turn loop is a greedy Markov chain: given context C_t, the model emits action a_t, receives observation o_t, updates C_{t+1} = C_t + a_t + o_t, repeats. No branching, no backtracking, no value estimation. Formally this is a depth-1 greedy policy on a POMDP with no lookahead.

(b) Hermes currently relies on the base model's implicit CoT via extended thinking tokens or system-prompt reasoning instructions. There is no structured intermediate output, no verification step, and no mechanism to detect when the agent is on a wrong track short of hitting max_turns.

(c) A principled approach inserts a lightweight scratchpad reasoning step before every tool call: emit a PLAN token sequence (current goal, next tool, expected outcome, abort condition) and a VERIFY token sequence after each tool result (did result match expectation? confidence 0-1). This is a structured CoT layer. No tree search needed; this is O(1) extra inference per turn. A simple decision rule: if VERIFY confidence < 0.4 on two consecutive turns, emit a self-correction turn before continuing.

(d) Value: high. Cost: prompt engineering only. Risk: token overhead per turn (roughly 80-120 tokens); mitigated by using Haiku for scratchpad and Sonnet for action. Validate by logging VERIFY confidence against task success rate across 50+ sessions.


Task Decomposition in delegate_task

(a) Decomposition maps a task T into a set of subtasks {T_1...T_n} with a dependency DAG G. Optimal decomposition minimises total latency subject to dependency constraints: min sum(cost(T_i) * critical_path_weight(T_i)). Currently Hermes ignores this; decomposition is done by the LLM ad hoc.

(b) The agent writes a free-form task description into each subagent context. No formal dependency encoding, no load estimation, no guaranteed completeness. Subtasks can overlap or leave gaps silently.

(c) A principled approach uses a two-phase protocol. Phase 1: generate a decomposition D = {(T_i, deps_i, output_schema_i)} as structured JSON before spawning any subagents. Score D on three criteria: coverage (does union of subtasks cover T?), independence (are non-dep pairs truly parallelisable?), verifiability (does each T_i have a checkable output contract?). Phase 2: spawn in topological order, passing verified outputs of dep tasks as context. The hermes-swarm-consensus skill already implements a reduction step — extend it with a coverage check against the original decomposition.

(d) Value: medium-high for tasks currently hitting 10-subagent limit or producing incomplete results. Cost: structured prompt engineering plus a JSON schema validator pass. Risk: decomposition prompt adds ~200 tokens upfront; LLM decomposition quality is itself unreliable. Validate by comparing task completion rate before/after on a fixed test set of 10 representative long tasks.


Multi-Step Planning in Long Tasks

(a) A long task is a trajectory tau = (s_0, a_0, ..., s_T) where T > max_turns is possible. Planning requires a value function V(s_t) to decide whether to continue, backtrack, or replan. Without V, the agent is running open-loop: no recovery from mid-task failure.

(b) Hermes uses context compression (summarise/prune) when context grows long. This is a lossy forward-only operation. There is no plan structure persisted across compression events, so the agent frequently loses track of sub-goals after a compression event.

(c) Maintain a lightweight plan object in the session file: {goal, completed_steps[], pending_steps[], current_depth, abort_conditions[]}. Before each compression event, extract and save the plan object separately (not subject to compression). After compression, re-inject the plan object as a structured prefix. This is analogous to a working-memory register in a cognitive architecture. A simple V approximation: V(s_t) = (completed_steps / total_estimated_steps) - (turns_used / max_turns). If V is declining, trigger a replanning turn.

(d) Value: high, especially for tasks that currently fail silently after compression. Cost: a small persistent plan file (write_file each turn), plan extraction prompt, plan re-injection in the context builder. Risk: plan file staleness if agent diverges from plan; mitigate by flagging divergence in VERIFY step above. Validate by measuring task completion rate on tasks > 30 turns.


Skill Sequencing

(a) Skill selection is a retrieval problem: given state s, choose skill k* = argmax_k sim(s, k). Currently this is tag/trigger matching — a sparse, binary retrieval function. The mathematical structure is nearest-neighbor search in an embedding space with a hard threshold.

(b) Tag matching is fast and interpretable but misses skills when phrasing diverges from tags. The agent also loads skills reactively (one at a time) rather than planning a sequence of skills needed for a multi-step task.

(c) Embed all skill descriptions (120 files, one-time) using a lightweight embedding model. At task start, retrieve top-5 skills by cosine similarity to the task description and load them proactively. Then apply a sequencing heuristic: sort by dependency (skills that produce outputs consumed by later skills go first). This converts reactive skill loading to a planned skill pipeline. The hermes-semantic-skill-routing skill already approximates this; the extension is the sequencing step.

(d) Value: medium. Current tag matching rarely fails catastrophically; the gain is reduced mid-task skill loading overhead. Cost: embedding index (one-time build, small), modified skill retrieval at task start. Risk: top-5 proactive loading adds ~2000 tokens of context at task start. Only worthwhile if task complexity justifies it. Use a complexity gate: apply proactive loading only when estimated task turns > 10.


Verification Gate Design

(a) A verification gate is a binary classifier G: (action, result) -> {pass, fail}. Optimal gate minimises expected cost of false passes (undetected errors propagating) plus false blocks (correct actions unnecessarily halted). This is a threshold on a learned score: pass iff V_gate(action, result) > theta, where theta is calibrated on held-out error cases.

(b) Hermes tool approval gates currently classify tool outputs by rule (keyword matching, output type, trust level). No learned component, no calibration against actual error rates.

(c) Train a lightweight classifier (logistic regression or small fine-tuned model) on (tool_name, output_summary, next_action_intent) -> error_probability using logged session data. Set theta to achieve < 5% false pass rate on a validation set. Use the VERIFY scratchpad step (from agent loop above) as a cheap pre-filter before invoking the heavier classifier.

(d) Value: medium-long term. Current rule-based gates are sufficient for known failure modes. A learned gate becomes valuable at scale when novel failure modes emerge. Cost: requires labelled error logs — start collecting now by flagging sessions where the agent self-corrected or hit max_turns. Validate when you have 200+ labelled examples.


IMPLEMENTATION CANDIDATES

1. Structured scratchpad reasoning (PLAN + VERIFY tokens per turn). Inserts lightweight CoT before every tool call and a confidence check after every result. Expected benefit: catches wrong-track reasoning early, reducing wasted turns and silent failures. Implementation cost: prompt engineering only, roughly one day; validate in one week against session logs.

2. Persistent plan object surviving context compression. A small JSON file updated each turn, re-injected after compression, with a simple V score for replanning triggers. Expected benefit: eliminates the most common failure mode in tasks longer than 30 turns. Implementation cost: two to three days for plan extraction prompt, file I/O hooks, and context builder modification.

3. Proactive top-k skill retrieval with sequencing gate. Build a one-time embedding index of skill descriptions; at task start retrieve and load the top 5 by similarity, ordered by dependency. Expected benefit: reduces mid-task skill loading latency and gaps in tasks with predictable skill pipelines. Implementation cost: one day for index build and modified retrieval; add complexity gate to avoid overhead on simple tasks.
