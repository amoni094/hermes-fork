PRIMER: Tool Use and Function Calling in LLM Agents

CORE CONCEPTS

Tool use in LLM agents is the capacity to ground generation in external state by issuing structured calls and conditioning subsequent generation on returned observations. Formally, the agent policy pi maps a context window C_t = (system, history, tools_schema) to either a tool call a_t = (tool_name, args) or a terminal response. The observation o_t = exec(a_t) is appended to C_t, producing C_{t+1}. This loop repeats until termination.

Three theorems structure the field:

ReAct theorem (Yao et al. 2022): Interleaving reasoning traces with tool calls reduces hallucination versus tool-call-only or chain-of-thought-only baselines. Condition: the reasoning trace must be grounded in prior observations, not free-form speculation.

Tool composition failure theorem: Composition error rate scales super-linearly with chain depth. If individual tool error rate is epsilon, a k-tool chain fails with probability approximately 1 - (1-epsilon)^k, amplified further by inter-tool data format mismatch. This is why agents fail on composition far more than on individual tools.

Documentation quality theorem: Call accuracy is a monotone function of schema completeness. Sparse or ambiguous schemas produce argument hallucination; enumerating valid values and error conditions measurably reduces malformed calls. No universal quantitative bound exists, but controlled studies show 15-40% accuracy lift from schema enrichment alone.

Tool selection is a policy problem: given task description d, tool inventory T, select a subset S subset T. Naive selection is bag-of-words similarity; principled selection is a learned or rule-based classifier over (d, T) with explicit composition feasibility checking. Error recovery requires an explicit retry policy: observe error type, classify (transient vs permanent vs argument fault), then branch to retry, reformulate, or fallback.


COMPONENT 1: TOOL-CALL LOOP

(a) Mathematical structure. The loop is a finite-horizon Markov Decision Process where states are context windows, actions are tool calls or responses, transitions are deterministic given exec(), and the reward is task completion. The key quantity is the expected number of turns to termination under policy pi.

(b) What Hermes does. Fixed per-turn loop: read context, emit tool call or response, append result, repeat up to max_turns. No explicit error classification per call result. No per-turn cost signal. The loop continues until the model self-terminates or hits the turn cap.

(c) Principled approach. Maintain a per-turn state machine with four transitions: success (append and continue), transient error (retry with exponential backoff up to N), argument fault (re-emit call with corrected args using error message as feedback), permanent failure (route to fallback tool or surface to user). Formally: classify o_t into {ok, transient, arg_fault, permanent}, then apply the corresponding handler before constructing C_{t+1}. Add a turn-cost accumulator; if accumulated cost exceeds budget, force early termination with partial result rather than silent failure.

(d) Value assessment. High value, low risk. The argument-fault classifier is the priority: most Hermes tool failures are malformed args (wrong path, wrong key name) that the model retries silently and wastefully. Implementation requires labelling ~50 error messages into the four classes and writing a router. Validate by measuring retry rate and wasted turns before and after. Risk: misclassifying a permanent error as transient causes wasted loops; conservative classification (default to permanent) is safer.


COMPONENT 2: TOOL APPROVAL GATES / HOOKS

(a) Mathematical structure. A gate is a binary classifier g: (tool_name, args, context) -> {approve, deny}. A trust score formulation extends this to a calibrated probability p_trust, with approval threshold tau. The ideal gate minimises false approval rate on dangerous calls subject to false denial rate below some operational tolerance.

(b) What Hermes does. Rule-based: certain tool names or arg patterns are flagged. The hook reads the tool output post-execution for trust classification. Pre-execution gating appears to be pattern-match only (no learned classifier, no calibrated confidence).

(c) Principled approach. Two-stage gating: pre-execution static analysis (arg pattern match plus schema validation, zero latency) then, for borderline calls, a lightweight classifier call using a cheap model (Mistral-small) scoring p_trust. Approve if p_trust > tau_high, deny if p_trust < tau_low, escalate to user if in between. Tune tau using a labelled dataset of historical tool calls split into safe/unsafe. For terminal calls specifically, parse the command into an AST and check against an allowlist of safe syscall patterns before scoring.

(d) Value assessment. Medium value for the current threat model (local use, trusted user). Worth implementing the pre-execution schema validation immediately: it is zero-cost, catches argument hallucination before execution, and requires no training data. The probabilistic classifier is worth building only if Hermes handles untrusted content (web-scraped code, user-supplied file paths) at scale. Validate by injection-testing the gate with known malicious patterns and measuring catch rate. Risk: overly restrictive gates break legitimate workflows; start with deny-on-schema-violation only.


COMPONENT 3: TOOL ERROR HANDLING

(a) Mathematical structure. Error recovery is a Bellman subproblem: given an error observation, choose the action that maximises expected task completion given remaining turn budget. The key decision variable is whether reformulation cost < expected value of retry.

(b) What Hermes does. Implicit: the model reads the error message in context and decides what to do next without an explicit policy. This works when the error message is informative and the model has seen similar patterns in training, but fails silently when error messages are opaque or the model enters a retry loop on a permanent failure.

(c) Principled approach. Explicit error taxonomy injected into the system prompt: map common tool error signatures to recovery actions. For web_search: 429 -> wait and retry; empty result -> broaden query; for terminal: non-zero exit + stderr -> parse stderr for known error classes; for browser: timeout -> retry once then fallback to web_extract. Add a loop-detection guard: if the same tool call appears twice with the same args, force arg mutation or escalation. Budget remaining turns into the decision: if turns_remaining < 2, skip retries and surface best available partial result.

(d) Value assessment. High value, directly measurable. Implement the loop-detection guard first: it is a three-line check and eliminates the most visible failure mode. Then add the terminal stderr parser. Validate by running a fixed task suite and measuring stuck-loop rate. Risk: low, these are additive guards.


COMPONENT 4: TOOL SELECTION GIVEN TASK

(a) Mathematical structure. Tool selection is a set cover problem over task sub-goals. Given task d decomposed into sub-goals g_1...g_k, select tools T_i for each g_i such that the composition T_1 -> T_2 -> ... -> T_k is feasible (output type of T_i matches input type of T_{i+1}).

(b) What Hermes does. Implicit: all tools are always in context schema. The model selects based on schema descriptions and training priors. Skills are pre-selected by tag-matching before the turn, which is an explicit but shallow retrieval step.

(c) Principled approach. Two-stage selection: (1) task classifier maps d to a tool subset S using a lightweight embedding similarity over tool descriptions, reducing the active schema to 5-8 tools; (2) composition feasibility check verifies that selected tools can chain (output/input type compatibility). This reduces schema tokens, sharpens the model's attention on relevant tools, and makes composition errors detectable before execution. Concrete formula: score(tool_i, d) = cosine(embed(d), embed(tool_i.description)), take top-K, then prune by type compatibility.

(d) Value assessment. Medium value. Hermes already does partial selection via skill loading. The incremental gain is schema pruning, which matters most when tool count exceeds ~15. Implementation requires embedding all tool descriptions (one-time) and a retrieval step per turn. Validate by measuring call accuracy on a held-out task set with full schema versus pruned schema. Risk: aggressive pruning removes a tool the model legitimately needs; use K >= 8 and include a fallback wildcard slot.


COMPONENT 5: TERMINAL / BROWSER / WEB_SEARCH TOOL POLICIES

(a) Mathematical structure. Each tool has a cost-accuracy profile: c(tool) and accuracy(tool, query_type). Optimal policy is argmin over feasible tools of c(tool) subject to accuracy >= threshold.

(b) What Hermes does. Priority ordering encoded in system prompt and skills (web_extract before browser, terminal preferred over browser for plain-text endpoints). This is a hand-coded policy that approximates the optimal but does not adapt to query type.

(c) Principled approach. Maintain a per-tool empirical accuracy table indexed by query type (structured data, live prices, JS-rendered, static text, API endpoint). At selection time, look up the table and route to the cheapest tool with empirical accuracy above threshold for that query type. Update the table from tool result quality signals (did the result contain the expected data type?).

(d) Value assessment. Low implementation priority; the existing hand-coded policy is already near-optimal for the query distribution Hermes sees. Worth revisiting only if tool costs become significant or a new tool type is added. Validate by logging tool outcomes and checking whether the empirical accuracy table matches the assumed priority order.


IMPLEMENTATION CANDIDATES (ranked)

1. Explicit error classifier + loop-detection guard in the tool-call loop. Classifies error observations into four types and blocks identical-call retries. Expected benefit: eliminates stuck-loop failures and wasted turns on permanent errors. Implementation cost: one classification function, one call history check, two days of work.

2. Pre-execution schema validation gate. Validates tool args against JSON schema before execution, surfacing argument faults before they reach the tool. Expected benefit: catches argument hallucination at zero execution cost, directly measurable by arg-fault rate. Implementation cost: schema validation library call in the hook layer, one day of work.

3. Embedding-based tool schema pruning at turn start. Reduces active tool schema to top-K most relevant tools per turn using cosine similarity over task description. Expected benefit: sharpens model attention on relevant tools, reduces schema tokens by 40-60% on focused tasks. Implementation cost: one-time embedding of tool descriptions, retrieval call per turn, three days including evaluation harness.
