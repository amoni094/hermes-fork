PRIMER: LLM Agent Evaluation and Benchmarking

CORE CONCEPTS

LLM agent evaluation is the discipline of measuring whether an agent reliably achieves intended goals across diverse, realistic conditions — not just whether it can solve a curated test set. Three structural problems dominate the field.

First, outcome-only metrics are necessary but insufficient. A binary success/failure signal over a full trajectory discards information about which sub-steps failed, creating high variance in gradient estimates and masking systematic weaknesses. The corrective is partial-credit scoring: decompose a task into a DAG of verifiable sub-goals, assign weights w_i to each node, and compute score = sum(w_i * s_i) / sum(w_i) where s_i is the sub-goal outcome. This correlates more tightly with deployment quality than end-state binary scores (Yao et al., WebArena; Trivedi et al., InterCode).

Second, LLM-as-judge evaluation introduces computable biases: position bias (judge prefers first response), verbosity bias (longer outputs rated higher), and self-enhancement bias (a model rates its own outputs higher). The calibration theorem states that an evaluator E is calibrated if E[E(x)] = E[human(x)] across the test distribution. Achieving calibration requires reference anchoring (giving the judge rubrics with concrete examples), swap-consistency testing (reverse the comparison order; a score flip indicates bias), and ensembling multiple judges from different families. A miscalibrated judge produces rankings that are monotone but offset — rankings correlate with human judgment but absolute scores do not.

Third, contamination inflates benchmark scores whenever training data overlaps with evaluation data. Contamination risk is proportional to test set age and public availability. Detection uses minimum-edit-distance overlap between training corpora and test prompts, or membership inference attacks (probing logit confidence on test instances vs. fresh paraphrases). Dynamic benchmarks — generated on the fly from templates, live data sources, or adversarial perturbation — are the structural defence.

Process-level evaluation audits the trajectory, not just the terminal state: which tools were called, in what order, with what arguments, and whether intermediate sub-goals were met. The key empirical result is that process-level correlation with human quality assessment is consistently higher (r > 0.7) than outcome-only correlation (r ~ 0.4-0.5) on multi-step tasks.


COMPONENT ANALYSIS: skillopt/GEPA SCORING

(a) Mathematical structure. Skill quality is a latent variable. The observable is task performance conditional on skill use: P(success | skill_version, task_distribution). GEPA applies Pareto-optimal search over a multi-objective fitness function: F(s) = [correctness, efficiency, coverage] where each dimension is independently scored. Genetic operators (crossover, mutation) produce candidate skill variants; the Pareto front selects non-dominated variants for promotion.

(b) What Hermes does. skillopt scores skill files on heuristics (length, keyword density, presence of examples, trigger specificity). GEPA runs mutation loops but the fitness signal is shallow: it uses self-assessed quality without grounding against task outcome data.

(c) Principled approach. Replace heuristic scoring with outcome-anchored evaluation: for each skill version v, collect a held-out probe set of tasks T where the skill is relevant. Compute F(v) = (1/|T|) * sum_t[w_outcome * outcome(t,v) + w_process * process_score(t,v) + w_efficiency * -tokens(t,v)]. Run Pareto search over (outcome, efficiency). Promote a new version only if it is non-dominated. This requires a replay harness that can rerun tasks with a pinned skill version.

(d) Value assessment. High value if you can build the replay harness; low value if fitness remains self-assessed. Risk: genetic search on shallow fitness amplifies noise — you get confident-but-wrong skill variants. Prerequisite: a task replay log with ground-truth outcomes for at least 50 tasks per skill family.


COMPONENT ANALYSIS: VERIFICATION-BEFORE-COMPLETION GATE

(a) Mathematical structure. This is a binary classifier on trajectory prefixes: gate(trajectory_prefix) -> {pass, fail}. The Bayes-optimal gate minimises E[cost_false_pass] + E[cost_false_fail]. For irreversible actions (file writes, deploys), cost_false_pass >> cost_false_fail, so the optimal threshold is very low (high recall of failures). Formally, pass iff P(trajectory_complete_and_correct | prefix) > threshold.

(b) What Hermes does. The skill runs a rule-based checklist: does the output contain expected fields, does a file exist, does a test pass. Rules are fixed and task-agnostic.

(c) Principled approach. Train a lightweight verifier V that scores P(correct | prefix, task_spec). Use process-level features: tool call sequence matches expected pattern, intermediate outputs pass type checks, no tool returned an error. At each gate activation, compute V(prefix) and compare to the task-specific threshold calibrated from historical data. For high-stakes tasks, escalate to LLM-as-judge with swap-consistency testing. Update V via online learning as new pass/fail outcomes accumulate.

(d) Value assessment. Moderate-high value; the rule-based checklist already works well for deterministic tasks (file presence, test pass). The marginal gain from a learned verifier is largest on fuzzy tasks (research summaries, code review). Risk: a poorly calibrated V creates false confidence. Validate by measuring verifier precision/recall against human spot-checks on 20 recent completions.


COMPONENT ANALYSIS: ADVERSARIAL-REVIEW SKILL

(a) Mathematical structure. Adversarial review is a two-player game: proposer P produces change C, reviewer R produces verdict V(C). The review is adversarial in the game-theoretic sense — R is incentivised to find defects. Calibration requires that R's defect rate matches ground-truth defect rate: P(R flags defect | defect exists) = recall, P(R flags defect | no defect) = false positive rate. A good adversarial reviewer maximises recall while controlling FPR.

(b) What Hermes does. A second model (gpt-5.6-sol via openai-api) reviews proposed changes and returns a verdict. The verdict is qualitative. There is no calibration of the reviewer's historical recall or FPR.

(c) Principled approach. Track reviewer calibration over time: for each review, record the verdict and the eventual ground-truth outcome (did the change cause a bug, test failure, or rollback?). Compute rolling recall and FPR. If FPR > 0.3, the reviewer is blocking too many valid changes — adjust the system prompt to be less conservative. If recall < 0.7, the reviewer is missing real defects — add adversarial test cases to the review prompt. Use swap-consistency: present the same change with arguments reordered; if the verdict flips, flag as low-confidence.

(d) Value assessment. High value with low implementation cost since the mechanism exists. The gap is purely measurement: you are not tracking whether the adversarial reviewer's flags are actually predictive of defects. Risk: uncalibrated adversarial review creates a veto bottleneck that blocks valid work — this is the "over-hardening" failure mode already flagged in your security-hardening-balance-review skill. Implement calibration tracking immediately.


IMPLEMENTATION CANDIDATES (RANKED)

1. Adversarial reviewer calibration tracking.
What it is: a lightweight log that records each adversarial-review verdict alongside the eventual outcome (merged cleanly, reverted, bug filed), then computes rolling recall and FPR.
Expected benefit: makes the existing adversarial-review skill evidence-backed instead of opinion-backed, directly reducing both false blocks and missed defects.
Implementation cost: one append-only JSONL log, one weekly cron job computing precision/recall — two hours of work with no architectural change.

2. Process-level task scoring for the verification gate.
What it is: augment the completion gate with a structured trajectory audit — tool sequence, error counts, intermediate output checksums — scored against a per-task-type rubric.
Expected benefit: catches trajectories that reach the correct terminal state via a broken path (lucky outcomes), which the current checklist misses entirely.
Implementation cost: define rubrics for the top five task types, instrument the tool-call loop to emit a structured trace, write a scorer — roughly one day of work with a two-week validation period.

3. Outcome-anchored GEPA fitness with a task replay harness.
What it is: replace skillopt's heuristic fitness signal with measured task outcome rates from a held-out replay log, enabling principled Pareto selection of skill variants.
Expected benefit: genetic skill optimization produces variants that actually improve task success rates rather than gaming heuristic proxies.
Implementation cost: build a replay harness that can execute historical tasks with a pinned skill version (significant: one to two weeks), then wire into the existing GEPA loop. Prerequisite is the calibration logging from candidate 1 and 2.
