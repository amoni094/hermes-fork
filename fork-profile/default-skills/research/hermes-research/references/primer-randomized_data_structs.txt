PRIMER: Randomized Algorithms and Streaming / Persistent Data Structures

CORE CONCEPTS

Randomized algorithms introduce deliberate randomness to achieve guarantees that hold with high probability, often trading exactness for dramatic space or time reductions. The key distinction is between Las Vegas algorithms (always correct, random runtime) and Monte Carlo algorithms (bounded error probability, fixed runtime). Streaming algorithms process data in a single pass with sublinear memory, making them essential when data volume exceeds available RAM.

A sketch is a linear projection of a data stream into a compact structure that supports approximate queries. Linearity is critical: if sketch(A) and sketch(B) exist, sketch(A+B) can be computed without re-reading the data.

CountMin Sketch: Given epsilon (error tolerance) and delta (failure probability), maintain a w x d array of counters where w = ceil(e/epsilon) and d = ceil(ln(1/delta)). For each incoming item x, hash x with d independent hash functions h_1...h_d, increment count[i][h_i(x)] for each row. Point frequency estimate: min over all rows of count[i][h_i(x)]. Guarantee: estimate is between true frequency f and f + epsilon*N (where N is stream length) with probability >= 1 - delta. Space: O((1/epsilon) * log(1/delta)).

HyperLogLog: Estimates stream cardinality (distinct elements) using the position of the leftmost 1-bit in hashed values. With m registers, achieves standard error 1.04/sqrt(m). Space: O(m * log(log(max_cardinality))). For 1% error, m=1024 registers use ~1.2KB regardless of true cardinality.

Reservoir Sampling (Algorithm R): Maintain a reservoir of size k. For item i > k, include it with probability k/i, displacing a uniformly random existing element. Invariant: after seeing n items, each item is in the reservoir with probability exactly k/n. Space: O(k).

Persistent Data Structures: A persistent structure preserves all historical versions after updates. Path copying achieves full persistence on balanced trees with O(log n) time and space per update by copying only the O(log n) nodes on the path to the modified leaf. Fat nodes (storing version-stamped values at each node) achieve O(1) update space but O(log n) query time.

Amortized analysis assigns costs to operations such that the total amortized cost bounds the total actual cost. The potential method defines a potential function Phi over data structure states; amortized cost = actual cost + delta(Phi). This explains why hash table resizing is O(1) amortized: the doubling cost is pre-paid by insertions into the current table.


COMPONENT 1: Approximate Dedup in Research Sweep

(a) Mathematical structure: A research sweep produces a stream of document identifiers (URLs, paper hashes, titles). Deduplication is a set-membership problem over a stream. This maps directly to Bloom filters (probabilistic set membership, false positive rate epsilon = (1 - e^(-kn/m))^k) or MinHash-based near-duplicate detection (Jaccard similarity estimation via locality-sensitive hashing).

(b) Current Hermes behavior: URL-string exact matching within a session, with no cross-session dedup. Near-duplicates (same paper, different URLs; same story, different outlets) pass through as distinct items. The hermes-research skill deduplicates by title heuristically.

(c) Principled approach: Compute a 128-bit SimHash fingerprint for each document's text (or title+abstract). Two documents with Hamming distance <= 3 are near-duplicates with high probability for typical web content (established empirically; exact threshold depends on content type). Maintain a sorted list of fingerprints per sweep session. Cost: O(1) per document after hashing, O(log n) lookup. For cross-session dedup, a Bloom filter with m=100000 bits and k=7 hash functions gives false positive rate ~0.008 for n=10000 documents. Space: 12.5KB.

(d) Value assessment: Moderate. The real cost in research sweeps is LLM calls on redundant content, not storage. Eliminating 20-30% near-duplicate LLM invocations would have measurable token savings. Implementation is low effort (SimHash is ~40 lines of Python). Risk: SimHash false positives would silently drop non-duplicate content. Validate by running sweep with and without dedup on a fixed corpus of 200 papers and manually inspecting dropped items.


COMPONENT 2: Streaming Paper Count Estimation

(a) Mathematical structure: Counting distinct papers seen across multiple cron sweep runs is a cardinality estimation problem over a persistent stream. The stream is unbounded; exact counting requires O(n) space. HyperLogLog solves this in O(m * log(log(n))) space with 1.04/sqrt(m) relative error.

(b) Current Hermes behavior: Cron sweep jobs write results to files; the count of processed papers is implicit in file sizes or line counts read after the fact. No running estimate exists; tallying requires reading all output files.

(c) Principled approach: Maintain one HyperLogLog register array (m=512, ~768 bytes) per topic in a persistent file updated by each sweep run. After each run, merge the new sketch into the persistent one (HyperLogLog supports merging via bitwise max on registers). Report estimated distinct papers seen per topic with ~4.6% error. Cross-topic global count: merge all per-topic sketches in O(m) time.

(d) Value assessment: Low immediate value. The paper count is not a bottleneck decision variable in Hermes today. Worth implementing only if sweep deduplication logic needs a signal to throttle re-fetching. Cost is trivial (a Python datasketch library call). Risk: near-zero; sketch corruption can be detected by checksum.


COMPONENT 3: Persistent Memory Data Structures

(a) Mathematical structure: Hermes memory has three layers: session (ephemeral), hindsight (semantic vector index), and the Graphiti knowledge graph. Updates to these structures should be queryable at any prior version (for debugging, rollback, or audit). This is the persistent data structure problem: given a mutable structure, support both current-state queries and historical queries at cost O(log n) per operation.

(b) Current Hermes behavior: Hindsight and Graphiti are append-only in practice, but updates (promote/demote scores, entity merges) overwrite in place with no version history. The l1-promote pipeline can silently discard facts; the lifecycle.db has a taint_path field but no versioned state of the structure itself.

(c) Principled approach: Apply path-copying to the skill index (a trie or sorted array of ~120 skills). On each skillopt update, copy only the modified path nodes (O(log 120) = ~7 nodes). Store version pointers keyed by timestamp. For hindsight, treat each retain operation as appending to an immutable log; replay the log to reconstruct state at any timestamp. This gives full auditability with O(log n) overhead per write.

(d) Value assessment: Moderate-high for debugging; low for production throughput. The main win is auditability: when skillopt's GEPA loop degrades a skill, you can diff v(t) against v(t-k) to isolate the change. Implementation cost is moderate: requires refactoring skill storage to support versioned writes. Validate by intentionally introducing a bad skillopt update and confirming rollback restores prior behavior.


COMPONENT 4: Amortized Cost of Skill Index Updates

(a) Mathematical structure: The skill index (tag-to-skill mapping for ~120 skills) is updated on every skillopt pass. If updates trigger full index rebuilds, cost is O(n) per update. Amortized analysis asks: what is the total cost over T updates? If rebuilds happen at geometric intervals (1, 2, 4, ... T), total rebuild cost is O(T) amortized O(1) per update, identical to dynamic array resizing.

(b) Current Hermes behavior: The skillspector-guard maintenance skill runs validation passes; it is not clear whether skill index updates trigger full reloads or incremental patches. The hermes-semantic-skill-routing skill suggests tag-based routing without specifying index update granularity.

(c) Principled approach: Define a potential function Phi = (number of dirty skill entries since last full rebuild). Amortized cost per update = O(1) (patch one entry) + delta(Phi). Schedule a full rebuild when Phi exceeds sqrt(n) (about 11 skills for n=120). This bounds total rebuild cost at O(T + T/sqrt(n) * n) = O(T * sqrt(n)) for T updates, versus O(T*n) for rebuild-on-every-update. Decision rule: patch single skill entries during active sessions; rebuild only at session boundary or when dirty count >= 11.

(d) Value assessment: Low unless skill routing is measured as a latency hotspot. The index is tiny (120 entries); even a full rebuild is microseconds. Worth doing only as a hygiene discipline to avoid accidental O(n^2) behavior if skillopt ever runs at high frequency.


IMPLEMENTATION CANDIDATES (ranked)

1. SimHash near-duplicate filter for research sweeps. Eliminates redundant LLM calls on near-duplicate papers/articles across sweep runs; expected 15-25% token reduction on multi-source sweeps. Implement in a single ~50-line Python utility called before content is passed to LLM summarization; validate against a fixed 200-document corpus.

2. Versioned skill index with path-copying on skillopt writes. Enables rollback and diff-based debugging when GEPA degrades a skill; high diagnostic value given current opacity of skillopt loops. Requires refactoring skill storage to maintain a version log; one afternoon of implementation with validation via intentional bad-update test.

3. HyperLogLog persistent paper counter per sweep topic. Provides a lightweight distinct-paper-seen signal to throttle redundant re-fetching in cron sweeps; implementation is two lines with the datasketch library. Validate by comparing sketch estimate against exact count on a 1000-paper corpus; acceptable if error stays within 5%.
