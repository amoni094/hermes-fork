PRIMER: Verifiable Computation, ZK-Proofs, and Coding Theory


CORE CONCEPTS

Verifiable computation asks: can a weak verifier check a powerful prover's claim without redoing the work? Zero-knowledge proofs (ZKPs) answer a sharper question: can a prover convince a verifier of statement S without revealing any information beyond S's truth? Formally, a ZKP for relation R is a protocol where (a) completeness holds -- an honest prover always convinces, (b) soundness holds -- a cheating prover fails except with negligible probability epsilon, and (c) zero-knowledge holds -- the verifier learns nothing beyond validity, formalized by a simulator that generates transcripts indistinguishable from real ones.

Interactive proofs (IP) extend NP: the class IP equals PSPACE, meaning interactive protocols can verify much more than a static witness. Probabilistically Checkable Proofs (PCP) go further. The PCP Theorem states: every language in NP has a proof system where a verifier reads O(1) bits chosen adaptively, accepts correct proofs with probability 1, and rejects incorrect proofs with probability at least 1/2. This is extraordinary: constant query complexity suffices for NP verification.

Error-correcting codes are the substrate. A (n, k, d) linear code encodes k-symbol messages into n-symbol codewords with minimum Hamming distance d. The Singleton bound gives d <= n - k + 1; Reed-Solomon (RS) codes achieve this bound exactly. An [n, k, n-k+1]_q RS code evaluates a degree-(k-1) polynomial at n distinct field points. RS codes are locally decodable: given a corrupted codeword, you can recover any single message symbol by querying O(1) codeword positions (with randomization), correcting up to (n-k)/2 errors. Polynomial commitments build on this: a commitment to polynomial f(x) is a binding, hiding encoding from which the prover can later open f(z) for any z, with a succinct proof. SNARKs (Succinct Non-interactive ARguments of Knowledge) combine polynomial commitments with the Fiat-Shamir heuristic to make ZKPs non-interactive with proof size O(log n) or O(1) depending on construction.


HERMES COMPONENT ANALYSIS

-- Verifiable Agent Outputs --

(a) Mathematical structure. An agent output is a function f: context -> (action, result). Verifiability means showing that result is consistent with some attested computation over attested inputs. This maps to a commitment-and-proof scheme: commit to the context C and model weights W, then prove result = f(C, W) without re-running inference. In ZKP terms, the statement is "I know a witness (C, W, execution trace T) such that T is a valid execution of model f on C and T produces result."

(b) Current approach. Hermes trusts LLM outputs as-is. Tool-call results are read and forwarded to the next turn. There is no attestation layer, no hash of inputs, no proof that the output wasn't silently truncated or injected mid-pipe.

(c) Principled approach. Compute a Merkle commitment H = MerkleRoot(tokenize(context)) before each turn. After the turn, store (H, sha256(output), turn_id, model_id, timestamp) in a tamper-evident append-only log. For higher assurance, apply a STARK or Plonk proof over the tool dispatch trace: prove that tool_i was called with args_i and returned result_i, and that result_i was included unmodified in context_i+1. At minimum, the lightweight form is: for each turn, emit signed_output = Sign(sk, sha256(context || output)) where sk is a local key in a TPM or sealed file. Verifier checks signature chain on audit.

(d) Value assessment. Full ZKP over LLM inference is currently impractical -- inference circuits are enormous and ZK-SNARK compilation of transformer forward passes is a research frontier (zkML, 2024). The Merkle-log approach is practical today and costs under 1ms per turn. Worth implementing the log; hold the ZKP layer until zkML tooling matures. Risk: log can be selectively deleted; mitigate with remote write or signed checkpoint.


-- Tool Output Integrity --

(a) Mathematical structure. Tool calls form a directed acyclic graph: each node is (tool_name, args, result), edges are data dependencies. Integrity means the graph is self-consistent and each result is authentically produced by the claimed tool. This is an authenticated data structure problem: a hash-linked list or Merkle DAG over tool nodes.

(b) Current approach. Tool approval hooks classify outputs by heuristic (regex patterns, trust labels). No cryptographic binding between the tool invocation and the returned result. An adversarial web page or injected terminal output could alter results before they reach context.

(c) Principled approach. Wrap each tool executor in a thin attestation shim: result_hash = sha256(tool || args || raw_output); store (result_hash, timestamp) in lifecycle.db (already present in Hermes at ~/.hermes/memory-facts/lifecycle.db with taint_path and decision_hash fields). The hook classifier then checks: does the result_hash match an entry signed during this session? Reject if not. For the terminal tool specifically, record the PTY session hash; for web_extract, hash the raw HTTP response body before markdown conversion. This is a lightweight authenticated log, not a ZKP, but it closes the injection surface.

(d) Value assessment. High value, low cost. The infrastructure (lifecycle.db, hooks) already exists. Shim cost is negligible. The main risk is that hashing raw outputs before processing means the hash doesn't cover post-processing transforms -- document what the hash covers precisely. Validate by injecting a synthetic tampered result in a test harness and confirming the hook rejects it.


-- Agent Audit Trails --

(a) Mathematical structure. An audit trail is a sequence of signed state transitions: (s_0, a_0, s_1, a_1, ..., s_n) where s_i is context state and a_i is the action taken. Correctness of the trail means each transition is deterministic given (s_i, a_i) and the trail is consistent (no gaps, no rewrites). This is a hash chain: h_i = H(h_{i-1} || s_i || a_i).

(b) Current approach. Hermes logs session transcripts. l1-extract pulls facts post-session. There is no integrity protection on the transcript itself -- files are mutable, no chaining between turns.

(c) Principled approach. On each turn commit: chain_hash_i = sha256(chain_hash_{i-1} || turn_id || sha256(context_snapshot) || sha256(tool_calls) || sha256(model_output)). Store chain_hash_i in lifecycle.db alongside the existing decision_hash field. The l1-extract pipeline reads and verifies the chain before promoting facts: if chain_hash breaks, flag the session as potentially corrupted and quarantine promoted facts. Genesis hash chain_hash_0 = sha256(session_id || start_timestamp).

(d) Value assessment. Moderate value. Useful for debugging cron agent failures and adversarial review discrepancies. The chain doesn't prevent a compromised process from forging its own chain, so it's tamper-evident only against external modification (file edits, log truncation), not against a compromised agent process. Cost: one sha256 call and one DB write per turn. Implement after the tool integrity shim.


-- Skill Correctness Certificates --

(a) Mathematical structure. A skill is a procedural program: a sequence of instructions with preconditions P and postconditions Q. A correctness certificate is a proof that executing the skill on any input satisfying P produces output satisfying Q. In PCP terms: the skill execution trace is an NP witness; a PCP verifier would check O(1) steps of the trace to detect deviations. In practice this is program verification: encode skill as a finite automaton over tool-call sequences, check reachability of bad states.

(b) Current approach. skillopt/GEPA scores skill quality by LLM evaluation and task outcome heuristics. No formal precondition/postcondition specification. Skills are prose; correctness is inferred from whether tasks succeed.

(c) Principled approach. Add a structured header to each SKILL.md: PRECONDITIONS (required context keys, tool availability), POSTCONDITIONS (expected output properties), INVARIANTS (what must not change). On skill load, a lightweight checker verifies preconditions against live context. Post-execution, check postconditions programmatically where testable (e.g., file exists, exit code == 0, output matches regex). GEPA fitness function f(skill) then includes precondition-coverage rate and postcondition-violation rate, not just LLM quality score. Formally: f(skill) = alpha * task_success + beta * (1 - postcondition_violation_rate) + gamma * coverage. Set alpha=0.5, beta=0.3, gamma=0.2 as initial weights.

(d) Value assessment. High value for the GEPA loop specifically. Postcondition checking turns vague skill quality into a measurable signal. Implementation cost is moderate: requires annotating existing skills (120 files) and writing checkers for each postcondition class. Start with 5 high-frequency skills, measure false positive rate of the checker, then expand. Risk: over-specified preconditions block valid skill use; keep them permissive and tighten empirically.


RANKED IMPLEMENTATION CANDIDATES

1. Tool output integrity shim with lifecycle.db integration. Hash each tool's raw output before processing and verify in the approval hook. Expected benefit: closes prompt-injection and result-tampering surface with cryptographic evidence rather than heuristic labels. Implementation cost: one decorator per tool executor, two new columns in lifecycle.db, one hook rule -- under a day's work.

2. Per-turn hash chain for audit trails. Chain sha256 across turns and verify chain integrity in l1-extract before fact promotion. Expected benefit: detects external transcript corruption and gives cron agent failures a forensic baseline. Implementation cost: ten lines of Python in the turn loop and l1-extract, plus genesis hash at session start.

3. Skill postcondition checking integrated into GEPA fitness. Add structured PRECONDITIONS/POSTCONDITIONS headers to the top-10 most-run skills and score violations in the GEPA loop. Expected benefit: converts skill optimization from LLM-opinion-based to partially machine-verifiable, improving GEPA convergence quality. Implementation cost: two to three days to annotate skills, write checker dispatch, and wire into GEPA fitness function.
