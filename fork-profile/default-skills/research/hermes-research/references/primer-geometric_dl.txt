PRIMER: Geometric Deep Learning and Equivariant Neural Networks

CORE CONCEPTS

Geometric Deep Learning (GDL) is the program of building neural networks that respect the symmetry structure of their input domain. The central insight, formalised by Bronstein et al. (2021), is that virtually every successful deep learning architecture — CNNs, RNNs, Transformers, GNNs — can be derived as a special case of enforcing the right symmetry group on a signal space.

A symmetry group G acts on a domain X. A function f: X -> Y is equivariant under G if f(g.x) = g.f(x) for all g in G, and invariant if f(g.x) = f(x). Equivariance means the output transforms predictably with the input; invariance means output is unchanged. CNNs are translation-equivariant over grid domains. The goal is to impose whichever symmetry is present in the problem structure.

Graph Neural Networks formalise computation over graph-structured data. In the Message Passing Neural Network (MPNN) framework (Gilmer et al., 2017), each node updates its state by aggregating messages from neighbours: h_v^(t+1) = UPDATE(h_v^(t), AGG({MSG(h_v^(t), h_u^(t), e_uv) : u in N(v)})). Aggregation must be permutation-invariant (sum, mean, max). The Weisfeiler-Lehman (1-WL) theorem states: MPNNs are at most as powerful as the 1-WL graph isomorphism test. They cannot distinguish graphs that 1-WL colours identically. Higher-order WL (k-GNN) breaks this ceiling at exponential cost.

Equivariant networks for 3D geometry enforce SO(3) (rotational) or SE(3) (rotational + translational) equivariance. SE(3)-Transformers, SEGNN, and Tensor Field Networks represent features as irreducible representations (irreps) of SO(3) and mix them via Clebsch-Gordan tensor products. This guarantees generalisation across orientations with no data augmentation, at the cost of restricted nonlinearities and higher compute.

The GDL blueprint prescription: identify the symmetry group of your problem, construct the equivariant function class, restrict expressiveness only as far as needed.


COMPONENT 1: GNN OVER SKILL DEPENDENCY GRAPH

(a) Hermes has ~120 skill files, each with a trigger string and a category. The dependency structure — which skills reference or load others, which co-occur in sessions, which share tool subsets — is a directed attributed graph G = (V, E, X) where V = skills, E = co-activation or explicit load edges, X = tag/trigger embeddings.

(b) Currently: tag-matching heuristic. A skill loads if a keyword from the user query hits its trigger string. No structural reasoning over the skill graph; no propagation of relevance through dependency paths.

(c) A principled MPNN would embed each skill node, propagate relevance scores along dependency edges, and score all skills in a single forward pass: s_v = READOUT(h_v^(L)), where h_v^(L) is the L-th layer node embedding. Retrieval becomes: rank skills by s_v, threshold at top-k. This exploits transitivity (if skill A loads skill B, and A is relevant, B's prior goes up) and co-activation patterns learned from session logs. The graph is small (~120 nodes), so a 2-layer GCN is trivially cheap at inference time.

(d) Honest assessment: moderate value. The bottleneck today is trigger string quality, not retrieval architecture. A GNN only helps if the skill graph has meaningful structure that tag-matching misses. You need to instrument which skills load together in successful vs failed sessions, build that edge set, and then measure precision@k improvement. Risk: skill graph is sparse and changes as skills are added — model retraining cadence becomes a maintenance cost.


COMPONENT 2: GRAPH-STRUCTURED MEMORY IN GRAPHITI

(a) Graphiti stores entities and facts as a knowledge graph KG = (E, R, T) where E = entity nodes, R = typed relation edges, T = temporal episode index. This is a heterogeneous attributed graph. Queries are semantic similarity lookups over node/edge embeddings. The structure has clear symmetry: entity identity is invariant to the order in which facts were ingested (permutation invariance over episodes), and temporal recency should decay smoothly.

(b) Currently: Graphiti retrieves by vector similarity and keyword match. Relation edges are used for graph traversal but not as first-class signals in the retrieval score. There is no propagation of relevance through the entity graph — a fact two hops away from a matched entity is not surfaced unless explicitly traversed.

(c) A principled approach applies R-GCN (Relational GCN, Schlichtkrull et al. 2018) over the KG: h_v^(t+1) = sigma(sum_r sum_{u in N_r(v)} (1/c_{v,r}) W_r h_u^(t) + W_0 h_v^(t)). Each relation type r has its own weight matrix W_r. This lets "is-instance-of", "caused-by", "co-occurs-with" relations contribute differently to relevance propagation. Combined with temporal decay (weight edges by exp(-lambda * delta_t)), the retrieval score becomes graph-aware, not just embedding-similarity-aware.

(d) Honest assessment: high potential but high integration cost. Graphiti is a third-party service; you cannot easily swap its retrieval internals for an R-GCN without forking or wrapping it. Validate first by measuring recall on known fact chains — if multi-hop retrieval is already a failure mode in practice, the case is strong. Risk: KG schema changes break the R-GCN weight matrices; you need a stable schema first.


COMPONENT 3: EQUIVARIANT PROCESSING OF STRUCTURED AGENT STATE

(a) At each turn, Hermes has a state vector: current tool outputs, model routing decision, context length, active skills, compression ratio. This is a structured tuple, not inherently geometric. However, the routing decision is a function of features that have natural symmetry: if you permute the candidate models or permute the available tools, the optimal policy should permute correspondingly. This is a permutation-equivariance requirement over sets.

(b) Currently: model routing is a rule table in config.yaml — explicit if/then conditions on task type, context length, cost tier. Tool approval gates are threshold classifiers on individual tool outputs with no joint reasoning over the tool set.

(c) A principled approach represents the candidate model set and tool set as sets (not ordered lists) and applies a Deep Sets or Set Transformer architecture: f({x_1,...,x_n}) = rho(sum_i phi(x_i)), which is provably permutation-invariant. For routing, phi encodes each model's capability profile and current context features; rho outputs a score vector over models. This is equivariant to adding/removing models from the pool — adding a new model does not require rewriting routing rules, only adding its feature vector. For joint tool-output trust scoring, a Set Transformer over the current turn's tool outputs gives a trust score that accounts for corroboration across tools.

(d) Honest assessment: low-to-moderate value near-term. The current rule table works well and is interpretable. Set Transformer routing would require a training dataset of (context, model choice, outcome quality) triples — which Hermes does not currently collect systematically. The architecture is the right long-term direction as the model pool grows and routing rules become unmaintainable. Validate by first instrumenting routing decisions and outcomes for 4-6 weeks, then check whether rules are being violated or causing visible quality drops.


RANKED IMPLEMENTATION CANDIDATES

1. Skill retrieval GNN
What: A 2-layer GCN over the 120-node skill dependency graph, replacing keyword-trigger matching with propagated relevance scores.
Expected benefit: Catches transitively relevant skills that keyword matching misses, reducing failed retrievals in complex multi-skill tasks.
Implementation cost: Low — build the edge set from session co-activation logs, train offline on ~500 annotated sessions, inference is a single CPU forward pass per turn.

2. R-GCN wrapper for Graphiti multi-hop retrieval
What: An R-GCN scoring layer over Graphiti query results, reranking retrieved facts by graph-propagated relevance rather than pure vector similarity.
Expected benefit: Surfaces causally or relationally connected facts that are embedding-distant, improving memory recall on complex reasoning tasks.
Implementation cost: Medium — requires stable Graphiti schema, a wrapper that fetches the local neighbourhood of matched entities, and a labelled evaluation set for recall measurement.

3. Set Transformer for model routing
What: A permutation-invariant neural router that scores candidate models as a set given the current turn's feature vector, replacing the config.yaml rule table.
Expected benefit: Routing generalises automatically to new models and degrades gracefully as the pool changes, without manual rule maintenance.
Implementation cost: High — requires systematic outcome labelling, 4-6 weeks of instrumented data collection before training is feasible; do not implement without that data.
