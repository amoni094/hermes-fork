PRIMER: Mixture of Experts Theory

================================================================================
FIELD OVERVIEW

Mixture of Experts Theory studies conditional computation: how to route subsets of input to specialized processors (experts) rather than running all computation paths universally. The field originated in the 1990s (Jacobs et al.) and has crystallized around sparse gating networks where a learned router selects k experts from a pool of n, keeping total compute roughly constant while scaling model capacity. Core objects are the gating function (learns routing probabilities), load balancing objectives (prevent expert collapse where one expert absorbs all traffic), and capacity factors (ratio of expert capacity to average load). Mathematically, this is a conditional expectation problem: decompose the input space into regions where different experts specialize, then learn both the partition and the expert parameters jointly. The field matters because it decouples model capacity from compute cost—the hard constraint that limits dense scaling. For distributed systems and multi-agent orchestration, sparse routing also maps naturally onto heterogeneous resources (different APIs, local vs. cloud inference).

================================================================================
KEY RESULTS

1. LOAD BALANCING IS FUNDAMENTAL (Not Optional)
Without explicit load balancing loss, gradient flow drives all examples to the single best expert. This causes expert collapse and wastes capacity. The standard auxiliary loss is:

  L_aux = alpha * sum_i (load_i / capacity_i) * (gate_i / n)

where load_i is the count of examples routed to expert i, capacity_i is its throughput/token limit, gate_i is the sum of routing probabilities to expert i. This term must be added to the primary loss during training.

2. TOP-K ROUTING APPROXIMATION
The gating network outputs softmax(logits) over n experts, but selecting top-k (instead of sampling all) is differentiable via straight-through estimators or concrete distributions. For k << n, this reduces compute by n/k. The approximation error in gradient estimates decreases as k increases; empirically k=2 to k=4 works well even with n=256.

3. MOE SCALING LAW
With fixed compute budget C, a MoE model scales better than dense: dense loss drops as C^{-a} (typically a ≈ 0.07), but MoE loss drops as C^{-b} where b ≈ 0.13. Doubling experts without increasing per-expert compute improves loss roughly 30% more than doubling dense parameters within the same budget. This is why scaling works: capacity grows, compute stays flat.

4. EXPERT SPECIALIZATION EMERGES
Even with no explicit specialization signal, experts naturally partition the input space if routed jointly with load balancing. Downstream analysis (e.g., probing or attention patterns) reveals each expert develops distinct sensitivity profiles. This is not guaranteed; it requires the gating network to have sufficient expressiveness and load balancing to prevent collapse.

================================================================================
STANDARD PRACTITIONER TOOLS

Load balancing auxiliary loss implementation: compute per-expert counts in each minibatch, divide by capacity, multiply by mean gate logits, weight by 0.01-0.1 coefficient and add to total loss.

Router softmax + top-k sampling: use categorical distribution over n experts, select top-k by probability, apply stop-gradient on softmax denominator to avoid probability mass collapse.

Expert capacity factor: set capacity = (batch_size * seq_len * k) / n * (1 + slack), typically slack = 0.25. Drop tokens exceeding capacity or use overflow routing (send excess to second-choice expert).

Auxiliary loss strength tuning: start at 0.01, increase if load imbalance (measured by std of expert loads) exceeds threshold, decrease if experts under-specialize.

HERMES APPLICATIONS

APPLICATION 1: MODEL ROUTING (Each LLM as Expert)

(a) Mathematical structure:
Hermes selects among Claude, GPT, Grok, Mistral, Mistral-Small for each subtask. This is a mixture of experts where each expert is a language model with different inference costs, latency, and capability profiles. The gating function learns a routing policy over a feature vector representing task properties (domain, reasoning depth, token budget, security tier). The "mixture" output is the weighted combination of model responses, typically aggregated via hermes-swarm-consensus.

(b) Current heuristic:
Hermes likely routes based on explicit rules: "use Claude for reasoning, GPT for math, Mistral-Small for fast tasks." This ignores learned specialization and doesn't balance load across API quotas or cost constraints.

(c) Principled approach from MoE theory:
Train a lightweight gating network (2-3 layer MLP) on historical task outcomes. Input features: task embedding (from skill label + context), estimated token count, domain tag, time budget, available quota. Output: softmax over 5 models. Add load balancing auxiliary loss penalizing uneven model usage (measured by tokens or API calls per model per hour). During inference, route using top-k=2 or k=1 if budget is tight. Learn routing offline on 1-2 weeks of task logs; retrain weekly. Formula:

  routing_logits = MLP(task_embedding + token_budget + domain_onehot)
  routing_probs = softmax(routing_logits)
  selected_models = top_k(routing_probs, k=2)
  L_total = task_loss + 0.05 * L_load_balance

(d) Worth implementing?
HIGH VALUE, MEDIUM EFFORT. Hermes already has diverse models; learning to route avoids redundant API calls and speeds average latency. The gating network is tiny (< 1M params). Risk: routing quality depends on task logging granularity. If logs lack outcome signals (did the model's response actually solve the task?), learned routing collapses to model priors. Mitigation: ensure each task_log entry includes a quality score (human feedback, downstream success, or tool return code). Implementation time: 1-2 days. ROI: 15-25% reduction in token spend and 10-20% latency improvement if routing avoids slow models on fast tasks.

APPLICATION 2: SKILL SELECTION (Procedural Knowledge Routing)

(a) Mathematical structure:
Hermes loads "skills" (procedural knowledge files) per task type. Skill selection is routing: given a task, select which skills to load and weight. Each skill is an expert in a subdomain (e.g., "web_scraping.skill", "math_reasoning.skill"). The gating function learns the relevance of each skill to the task context. The mixture output is a ranked skill set that the agent loads into its tool-call loop.

(b) Current heuristic:
Hermes routes by task_type key or manual task->skill mapping. No learned ranking; skills are binary (loaded or not) rather than weighted.

(c) Principled approach:
Train a skill routing MLP on (task, selected_skills, outcome) tuples. Input: task_embedding (description + context), available_skills metadata (name, domain tags, prerequisite skills). Output: logits over n skills. Top-k skill selection or soft weighting. Load balancing loss prevents all tasks from selecting the same popular skill (e.g., always loading "parse_html"). Capacity factor: if n_skills = 50 and you want k=3 per task, capacity per skill ≈ (batch_size * 3) / 50. Add auxiliary loss penalizing Gini coefficient of skill load.

During inference, compute skill routing logits, select top-k=2-4 skills, load them into memory, run ReAct loop. Formula:

  skill_logits = skill_router_MLP(task_embedding, skill_metadata)
  skill_probs = softmax(skill_logits)
  selected_skills = top_k(skill_probs, k=3)
  L_aux = alpha * entropy(load_per_skill) + beta * (load_imbalance_penalty)

(d) Worth implementing?
MEDIUM-HIGH VALUE, LOW EFFORT. Skill loading is already modular; the router is another MLP. But the payoff depends on whether skills actually specialize. If most tasks benefit from most skills, routing provides no savings. Test this first: compute pairwise correlation of skill usage vs. task outcome. If correlation is weak, skip. If strong (> 0.3), implement routing. Effort: 1 day. Risk: cold-start problem if new skills arrive without training data. Mitigation: use skill metadata (domain tags) as fallback features.
