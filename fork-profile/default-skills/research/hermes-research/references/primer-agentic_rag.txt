PRIMER: Agentic RAG and Context Management

CORE CONCEPTS

Retrieval-Augmented Generation (RAG) grounds language model outputs by injecting retrieved documents into the context window before generation. Agentic RAG extends this: the model itself decides when to retrieve, what to retrieve, and whether to retrieve again. This turns retrieval from a static preprocessing step into a dynamic loop within the agent's decision cycle.

Key definitions:

Relevance score r(q, d): a scalar measuring semantic overlap between query q and document d. Common implementations: BM25 (lexical), cosine similarity over dense embeddings (semantic), or a trained cross-encoder reranker. The retrieval oracle selects top-k by r.

Context window C: fixed token budget T. Each document d_i costs t_i tokens. The retrieval problem is a constrained knapsack: maximize sum(r(q, d_i)) subject to sum(t_i) <= T.

Multi-hop retrieval: for query q requiring reasoning chain q -> q1 -> q2 -> answer, single-shot retrieval fails because q1 is latent in the answer to the first retrieval. Solution: condition each retrieval on prior results, treating it as a Markov chain over query states.

Context compression: given a retrieved passage p with length n tokens, produce summary s with length m < n tokens preserving information relevant to q. Semantic preservation condition: KL(P(a|q,p) || P(a|q,s)) < epsilon for answer distribution P(a|·).

Key empirical results (broadly replicated across benchmarks):

Iterative retrieval (2-4 hops) outperforms single-shot on multi-faceted queries by 15-30% F1, but adds latency proportional to hop count. Relevance-gated retrieval (retrieve only when model confidence < threshold) reduces irrelevant context by 40-60% with negligible recall loss. Semantic compression (extractive or abstractive summaries conditioned on the query) preserves 85-95% of answer-relevant content at 30-50% compression ratios. Truncation preserves 60-70%.


COMPONENT ANALYSIS

--- Context Compression ---

(a) Mathematical structure. Compression is a lossy channel: f: (p, q) -> s where |s| < |p|. Optimal f minimizes len(s) subject to mutual information I(a; s|q) >= I(a; p|q) - delta. This is a rate-distortion problem. Distortion is measured against downstream answer quality, not token count.

(b) What Hermes does. Hermes compresses conversation history by summarizing old turns when context nears the budget. This is query-agnostic: the compression ratio is set by config.yaml thresholds and the summary is not conditioned on the current task. Early turns are treated as equally compressible regardless of whether they contain critical tool results.

(c) Principled approach. Condition compression on the current turn's tool calls and goal. Score each context segment by relevance to the current active query using a fast embedding comparison (e.g. MiniLM). Compress low-relevance segments first. Use extractive selection (keep top-K sentences per segment by relevance score) rather than abstractive summarization for tool outputs, which tend to be structured and loss-sensitive. Formula: for segment s_i, keep if cos(embed(s_i), embed(q_current)) > tau, else summarize to top-3 sentences by score.

(d) Value: High. Query-conditioned compression is the highest-leverage change here because it directly reduces context noise per turn without adding retrieval latency. Risk: the fast embedding model must be local (no API cost per turn); MiniLM or a quantized all-mpnet-base runs on CPU in <50ms. Validate by comparing answer quality on a held-out set of multi-turn tasks with and without conditioned compression. Implement tau as a tunable config.yaml parameter.


--- Hindsight Recall ---

(a) Mathematical structure. Hindsight is a semantic memory bank. Recall is a nearest-neighbor search: given query q, return top-k facts by cos(embed(q), embed(f_i)). The challenge is the precision-recall tradeoff: low k = low recall, high k = context bloat. Reranking addresses this: retrieve top-50 by ANN, then score by cross-encoder, keep top-10.

(b) What Hermes does. Hindsight injects relevant memories at session start via semantic search. The recall k is fixed. There is no per-turn recall trigger; memories are not retrieved mid-task in response to tool results uncovering new sub-queries.

(c) Principled approach. Add a mid-turn recall gate: after each tool result, extract the named entities and key claims from the result, embed them, and run a fast cosine lookup. If any memory scores above tau_recall, inject it into the next prompt prefix. This is the "forward-chaining" pattern: new evidence triggers memory retrieval, which may reveal further relevant context. Decision rule: if max(cos(embed(tool_result_excerpt), embed(f_i))) > 0.82, prepend matching facts to next turn.

(d) Value: Medium. Useful for tasks where mid-task discovery should surface prior knowledge (e.g. a web search result mentions a company Hermes has facts about). Risk: false positive injections add noise. Start with a high threshold (0.85) and entity-only triggering rather than full result embeddings. Cost is low if Hindsight already has fast local search.


--- Skill Selection ---

(a) Mathematical structure. Skill selection is a classification problem: given turn context x, choose skill s from set S (or null). Ideal: P(s|x) learned from successful task trajectories. Current heuristic: tag/trigger string matching, which is precision-focused but misses paraphrase variants.

(b) What Hermes does. Skills are matched by keyword/trigger strings in their frontmatter. Hermes scans available skills and loads those whose triggers match the user message. This is fast but brittle: a query phrased differently than the trigger is missed; unrelated skills can match on common words.

(c) Principled approach. Embed each skill's description and trigger set offline (one-time). At turn start, embed the user message plus recent context window (last 3 turns). Compute cosine similarity to all skill embeddings. Return skills above threshold plus the top-3 by score regardless of threshold (floor guarantee). Use a reranker (cross-encoder) on the top-10 to reduce false positives. This adds ~30ms per turn with a local model. Formula: candidates = {s : cos(embed(x), embed(s)) > 0.70} union top3(scores), then rerank.

(d) Value: Medium-high. The skill library is large (~120 skills) and growing; string matching becomes more brittle as the library grows. Semantic matching generalises better. Risk: semantic matching requires maintaining skill embeddings as an index file, which must be rebuilt when skills are added. Moderate implementation cost; validate on a sample of 50 tasks where the correct skill was known but missed by string matching.


--- Web Search and Web Extract Pipeline ---

(a) Mathematical structure. The pipeline is a two-stage retrieval funnel: web_search returns O(5-10) URLs ranked by search engine score, web_extract converts each to text, then the model reads all extracts. This is retrieve-then-read. The key issue is no re-ranking between retrieval and reading: all extracted pages enter context at equal weight regardless of query relevance.

(b) What Hermes does. web_search returns results, web_extract fetches them. The model reads all extracts in full or truncated by char_limit. There is no explicit relevance filtering between search and extract; the model must implicitly ignore irrelevant content.

(c) Principled approach. After extraction, score each extract's top-5 sentences against the query by BM25 or cosine similarity. Drop extracts scoring below a floor (e.g. max sentence score < 0.4). For retained extracts, compress to top-10 relevant sentences rather than passing full content. This reduces context cost per search action by 40-70% on typical queries. Algorithm: for each extract e, score = max(BM25(q, sent) for sent in sentences(e)); if score < floor, discard; else keep extract compressed to top_k sentences by score.

(d) Value: High and immediately actionable. Web extract passes multi-thousand-token pages into context regularly. A relevance-gated extract compressor reduces token cost per search-heavy task by a meaningful margin. Risk: overly aggressive filtering drops useful but tangentially relevant context. Use per-result score logging to tune the floor parameter. Implement as a thin wrapper around web_extract; no model change required.


--- agentic_rag skill ---

Not found in the current skill library. This is a gap. The described components (iterative retrieval, relevance gating, multi-hop) are implemented ad hoc per task or not at all. An explicit agentic_rag skill would encode the retrieval loop, scoring thresholds, and compression decisions as reusable procedure.


TOP 3 IMPLEMENTATION CANDIDATES (ranked by expected value / cost)

1. Web extract relevance filter and compressor. Score each extracted page against the query after fetch, discard low-relevance pages, compress retained pages to top-10 sentences. Expected: 40-60% token reduction on search-heavy tasks with minimal recall loss. Cost: one wrapper function, no model or infra change, tuneable via config thresholds.

2. Query-conditioned context compression. Re-score existing context segments against the current query before compressing, prioritising relevance-low segments for aggressive compression. Expected: reduces context noise in long multi-tool sessions, directly improving model attention on relevant evidence. Cost: requires a local embedding model (MiniLM) already usable for other components; config.yaml parameter for tau.

3. Semantic skill selection index. Embed all skill descriptions offline into a vector index; at turn start, retrieve candidates by cosine similarity and rerank, replacing pure string matching. Expected: catches skill matches missed by paraphrase variants, reduces false positives as library scales. Cost: moderate; requires index build step and embedding model; validate against a curated miss-rate sample before replacing string matching.
